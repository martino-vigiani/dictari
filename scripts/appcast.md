# Appcast & Sparkle release checklist

Dictari updates through Sparkle 2.x. This document covers the trust chain and the release command;
`scripts/release.sh` owns the lower-level build, signing, notarization, and DMG packaging.

## Update channel

Direct Xcode builds, local installs and public releases should use the same signing identity
(`DICTARI_SIGN_IDENTITY`, with `DICTARI_TEAM_ID`).
That shared designated requirement preserves the user's Accessibility and Microphone grants across
updates. Release builds read
`https://raw.githubusercontent.com/martino-vigiani/dictari-updates/main/appcast.xml`.
Versioned DMGs and deltas live under its stable GitHub release tag `updates`. The repository is
public because Sparkle clients need anonymous HTTPS access, but it contains no source code.

The EdDSA private key is stored in the login Keychain under account `dictari`. The matching public
key is committed in `Sources/Dictari/App/Info.plist`. Never rotate or delete this key: existing
installations only trust archives signed by it.

## One-time machine setup

If publishing from a new Mac, import the existing private key into its login Keychain. Do not
generate a replacement. Sparkle's `generate_keys` tool can export/import it explicitly:

```bash
generate_keys --account dictari -x /secure/offline/location/dictari-key
generate_keys --account dictari -f /secure/offline/location/dictari-key
```

Also create the notarytool keychain profile described at the top of `scripts/release.sh` and
authenticate GitHub CLI as an account allowed to publish the selected binary-only repository.

## Per-release flow

Run one command with a new semantic marketing version and a build number higher than the published
build. The script requires both values to increase, takes one authoritative feed-content/blob-SHA
snapshot, and rejects duplicates, regressions, malformed feeds, or network ambiguity before
building:

```bash
DICTARI_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
DICTARI_TEAM_ID="TEAMID" \
NOTARY_PROFILE="dictari-notary" \
./scripts/publish-update.sh 0.2.0 7
```

Each attempt uses a clean staging directory populated only from the live feed plus the requested
DMG. Exact candidate and generated bytes are retained under `build/update-transactions/`, with a
hash manifest, so an interrupted attempt can resume without rebuilding a different archive. The
script validates every pre-existing asset before uploading anything, probes every DMG/delta before
publishing, then updates the feed with the blob SHA captured at the start; a concurrent publisher
therefore fails the compare-and-swap instead of overwriting a newer feed. A release run looks like this:

```bash
DICTARI_UPDATE_REPO=martino-vigiani/dictari-updates \
DICTARI_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
DICTARI_TEAM_ID="TEAMID" \
NOTARY_PROFILE="dictari-notary" \
./scripts/publish-update.sh 0.1.3 4
```

After the feed is live the script also creates the GitHub release `v<version>` on the source
repository (`DICTARI_SOURCE_REPO`, default `martino-vigiani/dictari`) with the DMG attached as
`Dictari.dmg`, which keeps `releases/latest/download/Dictari.dmg` (used by `scripts/install.sh`) valid.

The script verifies that the `SUFeedURL` embedded in the app matches the selected repository.

## Checklist before publishing

- [ ] `SUFeedURL` and `SUPublicEDKey` still match the configured GitHub feed and Keychain key.
- [ ] `CURRENT_PROJECT_VERSION` is higher than the last release; bump `MARKETING_VERSION` for the
      user-visible release version too.
- [ ] `scripts/release.sh` completed `codesign`, notarization, stapling, and Gatekeeper checks.
- [ ] The publish script completed its public feed and archive probes.
- [ ] A previous installed version found and installed the release through “Check for Updates…”.

The first configured build is a bootstrap: older builds contain a placeholder public key and
cannot trust the feed. Install that bootstrap once via DMG; all later versions can self-update.
